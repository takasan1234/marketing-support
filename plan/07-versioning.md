# 07. バージョン管理・サイクル運用

## 基本方針

**履歴を残す（バージョニング）方式**を採用。

- 同じフレームワークに対して `v1`, `v2`, ... と履歴が積み重なる
- 「最新版」フラグ（`isLatest`）で区別
- 過去バージョンも閲覧・比較可能

## バージョン作成のタイミング

| 操作 | 挙動 |
|---|---|
| 初回入力 | `v1` を作成 |
| 軽微な編集 | 現在バージョンを上書き |
| 「新バージョン作成」ボタン押下 | `v + 1` を作成、前は履歴になる |
| 鮮度切れの生データを更新 → 連鎖更新 | 必要に応じて新バージョン提案 |

ユーザは「上書き」と「新バージョン」を意識的に切り替えられる。

## 生データのバージョン管理

生データ自体は基本的に**バージョン管理しない**（上書きまたは新規作成）。
理由：生データはそもそも事実情報のスナップショット。

ただし、`RawData.collectedAt` で取得日時を保持するので、過去のバージョンの FrameworkEntry が参照した生データの「当時の状態」を完全に再現するのは難しい。

→ 代替策：FrameworkEntry が参照した生データに対して、`FrameworkRawDataLink.contentSnapshot` フィールドを設けて、参照時点の `content` を保存する（将来追加）。

## バージョン履歴 UI

### フレームワーク編集画面のヘッダ
```
PEST 分析  [v3 (最新)]  [2026-05-19 更新]  [v1 v2 v3] [+ 新バージョン]
```

### 比較画面
- 左右に v1, v2 を並べて表示
- 変更箇所をハイライト
- 「Claude Code に差分を要約してもらう」ボタン

## サイクル運用シナリオ

### 初回（プロジェクト開始）
1. プロジェクト作成
2. PEST, 5Forces, 整理軸, VRIO の `v1` を作成
3. SWOT, クロスSWOT の `v1` を作成（上流の v1 を参照）
4. STP, 4P の `v1` を作成
5. KGI/KSF/KPI の `v1` を作成
6. 実施・運用

### サイクル目（3ヶ月後など）
1. 販売実績、顧客調査の新規生データ追加
2. ダッシュボードに「鮮度切れ：競合情報、SNS分析」など警告
3. 鮮度切れ生データを `/refresh-data` で再収集
4. 影響を受けるフレームワーク（5Forces, ポジショニング等）に黄色警告
5. SWOT の `v2` を作成（v1 をベースに、変化点だけ更新）
6. STP の `v2`、4P の `v2` も連動更新
7. v1 と v2 を比較して、「戦略がどう変わったか」を可視化

## 連鎖更新の扱い

フレームワーク A が更新されたとき、下流の B も自動更新するか？

**今回の方針：自動更新しない**。
- ユーザに「下流フレームワークも更新を検討」と通知のみ
- ユーザが意図的に下流を更新する
- 自動だと「いつの間にか変わってる」になり、サイクル運用の意識が薄れる

## ロールバック

過去バージョンを「最新」に戻したい場合：
- 新たに `v(latest + 1)` を作成し、過去バージョンの内容をコピー
- 「v3 は v1 のロールバック」とノートに記録
- 物理的な isLatest 付け替えはしない（履歴の純度を保つ）
